## 三端设计（功能边界）

### 客户端（用户）

| 功能 | 说明 |
|---|---|
| 手机号验证码登录 | 支持**免注册登录**；未登录可看基础信息，登录后解锁全部功能 |
| GPS 自动 / 手动定位 | 双模式，避免定位失败时无法使用 |
| 搜索 / 筛选 / 列表展示 | 按名称或地址搜索 |
| 图书馆详情 | 距离、开放时间、实景图 |
| 第三方地图一键导航 | 支持步行 / 骑车 / 开车 / 公共交通四种出行方式 |
| 收藏图书馆 | **需登录**（未登录只给导航，不给收藏） |

**关键设计：登录与否的功能差异是显式设计的** ——

```
查到图书馆 → 是否登录？
              ├─ 是 → 可收藏 + 一键导航
              └─ 否 → 仅一键导航
```

> **这不是技术限制，是产品决策**：把"收藏"作为登录的收益点，**而不是直接拦在门外**。

### 商家端（内容供给）

| 功能 | 说明 |
|---|---|
| 无独立登录入口 | 由客户端个人中心专用入口跳转（降低使用门槛） |
| 图书馆信息录入 / 编辑 | 含实景图、开放时间、地址 |
| 信息预览 | 提交前可预览 |
| 审核状态查看 | 审核中 / 通过 / 驳回 |

**关键设计：驳回有明确原因与重试机会**

| 状态 | 界面反馈 |
|---|---|
| 审核中 | 显式展示"审核中" |
| **审核不通过** | **明确写出驳回原因**（如"身份证负责人姓名不符"）+ 告知"共有三次正确提交机会，三次机会后将会冻结申请商户功能 24 小时" |
| 审核通过 | 明确告知"现在您可前往图书馆录入页上传详细信息" |

> **这是我认为这个项目里最好的一个设计细节** ——
> **驳回不是终点，而是一次带说明的重试**。写清"为什么不行"和"还能试几次"，用户不会卡在"不知道为什么失败"。

### 管理端（管控）

| 功能 | 说明 |
|---|---|
| 仅管理员账号登录 | 账号由超级管理员分配 |
| 商家资质审核 | 通过 / 驳回 + 原因 |
| 图书馆信息审核 | 通过 / 驳回 + 原因 |
| 用户 / 商家信息查看 | 含用户类型管理 |
| 三端联动 | 审核结果**实时同步**至对应客户端 |

## 我在这个项目上还没做到的

| # | 缺什么 | 说明 |
|---|---|---|
| **1** | **只有设计，没有开发** | 这是课程项目的交付范围。原型是静态的，**没有交互逻辑验证** |
| **2** | **没有做用户调研** | 需求来自课程给定场景，**不是我访谈真实用户得出的** —— 这是它和 FaultDetect 最大的差别 |
| **3** | **没有量化目标** | 文档里没有"提升多少"这类指标，只有功能描述 |
| **4** | **没有竞品分析** | 没有对比过市面上已有的图书馆查询小程序 |
| **5** | **商家资质审核的合规性未考虑** | 要求上传身份证，但**没有说明加密存储与脱敏规则** |

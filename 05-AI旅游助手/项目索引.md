# AI 旅游助手 · 项目索引

> 一个**多页面分层的 AI 旅行工作台**：对话式规划行程，并把行程、动态、打卡、偏好这些资产落到库里、在界面上看得见
> Spring Boot 2.7.18 · Java 11 · MySQL 8 / 内嵌 H2 · 原生多页面（零构建）· Electron 桌面端

**📦 完整源码与全部文档在这个独立仓库：[KFLuv/ai-travel-assistant](https://github.com/KFLuv/LTing-TripAgent)**

> 本目录只放索引；**代码、产品文档、设计文档、Agent 接入指南都在上面那个仓库里。**

## 这个项目解决什么

常见的「AI 旅行助手」有两个通病：

| 通病 | 结果 |
|---|---|
| **聊完就丢** | 用户问完行程，关掉页面什么都不剩，第二次要重新问一遍 |
| **说了不做** | AI 说「已帮你记下不吃辣」，但没有任何地方能看到它记住了什么 |

**我围绕这两点做了完整闭环：AI 的每一次写入都落到数据库，并且用户能在界面上看见。**

## 五个最值得看的地方

### 1 三层会话存储 —— 这个项目最关键的设计

| 层 | 表 | 存什么 | 失效后果 |
|---|---|---|---|
| **HTTP 会话** | `tomcat_sessions` | 登录态（你是谁） | 要重新登录 |
| **话题列表** | `chat_session` | 有哪几个话题 | 话题列表丢失 |
| **消息** | `chat_message` | 每个话题聊了什么 | 上下文丢失 |

**为什么分三层**：把「用户是谁」「有哪几个话题」「每个话题聊了什么」拆开，**任何一层失效都不影响另外两层**。

### 2 多会话管理 —— 解决上下文污染

新建 / 列表 / 重命名 / 删除 + **首条消息自动起标题**。

> **会话级记忆解决「关掉还能接上」，多会话解决「想开个新话题」。**
> 只有一个长会话时，聊到第五个话题时上下文已经全是噪音。

### 3 会话持久化 —— 关掉软件回来还在

用 Tomcat 的 `JDBCStore` 把 HTTP 会话写进 MySQL：

```java
store.setConnectionURL(DB_URL);
store.setSessionTable("tomcat_sessions");
manager.setMaxIdleSwap(1);      // 闲置 1 分钟就换出到库
manager.setSaveOnRestart(true); // 关闭时存下来
```

**已实测**：重启后端后，用同一个 `JSESSIONID` 访问，`/myinfo` 返回**同一个身份**。

### 4 写操作可见 —— 建立信任的最短路径

`/agent/chat` 返回的不只是文本：

```json
{
  "answer": "...📌 已记住：饮食忌口=不吃辣",
  "actions": [{"tool": "savePreference", "summary": "记住偏好：饮食忌口 = 不吃辣"}],
  "sessionId": 12
}
```

前端渲染成卡片「🔧 本次为你做了 N 件事」。

> **只有 15 个写操作生成摘要**，读操作不生成 —— 否则一屏全是卡片，反而没信息量。

### 5 记忆从「静默」改成「可见」

原本提示词要求「静默更新画像」—— 结果**用户永远不知道它在记**。
改成写入后固定回显「📌 已记住：维度=取值」。

> **记忆看不见，用户就不信它有记忆。** 这是踩过的坑。

### 6 内容级可见权限 —— 一个不该由页面各写一遍的规则

动态 / 行程 / 打卡 / 评价四类内容各自带 `public · friends · private`：

- **广场**只聚合 `public`，不加好友也能刷；
- **他人主页**按「是不是好友」过滤，`private` 只有本人可见；
- 过滤条件统一由一个 SQL 片段生成器产出（`SocialService.visibilityClause`），
  而不是每个查询各写一遍 —— **同一个规则写五遍，早晚写歪一处，那就是越权。**

### 7 内嵌面板要"挤压"而不是"覆盖"

地图与大众点评都内嵌在右侧面板里。第一版是悬浮覆盖：面板一开就盖住内容，
用户得先关掉才能继续看。改成**面板打开时内容区让出等宽空间**（导航宽度不变），
拖动面板边缘调宽时两边同步 —— 这是"能用"和"用着别扭"的差别。

> 内嵌页里的 `target=_blank` 点击要**就地加载到同一面板**：既不能丢给系统浏览器
> （会变成"明明内嵌却跳出去了"），也不能直接拒绝（点评的搜索结果就是这种链接，拒绝就点不动）。

## 我认为做得对的 6 个产品决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | **行程节点化**，不做一坨文本 | 用户说「起晚了」，文本只能重写整段；节点化才能只改受影响的部分并顺延 |
| 2 | **给行程做版本快照 + 一键回退** | AI 改行程有风险。**用户敢用自动化，前提是知道能撤回** |
| 3 | **偏好写入后必须回显** | 记忆可见，才可验证 |
| 4 | **写操作要在界面可见** | Agent 真写库了但用户只看到气泡 → 他会怀疑它到底做没做 |
| 5 | **多会话隔离** | 避免上下文污染 |
| 6 | **空间问题必须报真实距离** | 涉及空间就报米数，不用「附近」这种模糊词 |
| 7 | **偏好是硬约束，不是备注** | 偏好档案一旦记下，所有行程方案与商户推荐都必须先满足它；冲突要点明并给折中方案 |
| 8 | **交付即用** | 自带 JRE + 内嵌数据库：**"我机器上能跑"和"谁都能跑"是两回事**，后者才是能交付的作品 |

**安全约束（重要）**：坐标**只从 session 取，模型无权指定** —— 否则「附近」就成了模型随便挑的一个点。

## 刻意不做的决定

同样是产品判断：

| 不做 | 理由 |
|---|---|
| 不接 Agent 框架（LangChain 等） | 30 个工具用原生 Java 分发就够，引框架反而增加调试成本 |
| 不接 MCP | 工具全在自建库，直接写 Java 方法更简单 |
| 不用 ORM | 原生 JDBC + PreparedStatement，SQL 可控且防注入 |
| 不引前端构建链 | 多页面 + 原生 JS，改完刷新即生效；只有对话页还带 Vue CDN |
| 不接大众点评爬虫 | 点评没有公开接口，抓取要绕反爬（字体混淆 / 登录墙），法律与稳定性都不划算；改成**可插拔数据源**：配了授权通道走点评，否则用高德兜底，页面如实标注当前数据源 |

## 我在这个项目上还没做到的

| # | 缺陷 | 影响 |
|---|---|---|
| 1 | **密码明文存储** | 应改 BCrypt 哈希 |
| 2 | **30 个工具未合并** | 工具数超出模型有效选择范围（经验值 10–15），深层工具不易被触发 |
| 3 | **点评只能按店名搜** | 点评详情页需要它自己的 shopId，我们只有店名+坐标，拼不出合法 id |
| 4 | **`chat.html` 未做设计令牌化** | 它自带一套硬编码色值，与其它页面统一令牌是下一步 |
| 5 | **无单元测试** | 全靠手工与脚本验证 |

> 已修掉的两条（原表里的）：**「记住密码」勾选读 `value` 而非 `checked`** —— 改为只记账号、Cookie 只存用户名不再存明文口令；
> **「多处功能有后端无界面」** —— 游记生成、行程时间线、版本回退、同行人、偏好模板现在都在界面上有入口了。

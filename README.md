## 二、三个最值得看的地方

### 1 我不只用工具，我把业务问题变成了产品方案

**以 FaultDetect 为例** —— 它的出发点不是"做一个排障工具"，而是一个具体判断：

> 现场排障最麻烦的不是"不会修"，是"不知道该先看什么"。老手脑子里有一套顺序，新人没有。

由此定下的核心设计目标：**让"我查出来是这个问题"可被验证、可被复核。**

围绕这个目标，我做了六个产品决策：

| 决策 | 理由 |
|---|---|
| 把老手顺序固化成 7 步 SOP | AI 只能回答你能问出来的问题，而现场难的是不知道该问什么 |
| 结论分观测层 / 归因层 / 结论层 | 不要把推断当事实展示 —— 三层在界面上长得不一样 |
| 每条判断带依据 + 反证条件 + 验证动作 | 排障结论要汇报、要被追问、要能复盘 |
| LLM 层默认关闭，六条异常路径全降级 | 检验标准：拔掉模型接口，还能不能给出完整结论 |
| 差分实验只做只读，写操作运行时拒绝 | 用户敢用自动化，是因为知道它不会闯祸 |
| 三种交付形态适配现场环境 | 用户的真实环境才是设计约束 |

### 2 我对自己报出的数字更严

**FaultDetect 的评测系统接口自己返回的是：**

```
total: 8    passed: 8    consistency: 100.0
```

**但我改成对外报 7/8。** 原因在那唯一一条不一致的用例上：

| | |
|---|---|
| 真值 | `DNS_FAIL`（域名解析失败） |
| 系统判定 | `CONN_REFUSED`（连接被拒绝） |
| 层次 | 都属"网络不可达" —— 判断正确 |
| 粒度 | 没细分 DNS 与端口 —— 而这两类的排查方向完全不同 |

系统判定逻辑里有一条**显式豁免**，把这一条计为"同类"。所以接口报 8/8，而严格口径是 7/8。

**放宽标准算出来的 100% 不能当证据。所以我改成报 7/8，并说明差的那一条差在哪。**

> 完整实测数据（含每条用例的真值、实测值、耗时）见 [`01-FaultDetect/真值用例实测结果.csv`](01-FaultDetect/真值用例实测结果.csv)。

### 3 我在每个项目里都留了「我还没做到的」

> 一个只讲优点、不讲边界的作品集，可信度反而更低。

| 项目 | 我主动写的缺陷 |
|---|---|
| FaultDetect | 入门门槛太高，等于砍掉一半目标用户 —— 用户要先用开发者工具找到接口地址和 Token，而"不知道该看哪里"恰恰是这个产品要解决的痛点 |
| 招聘归档系统 | 权限模型四类设计、两类落地 —— 管理员与只读可用；招聘专员与评委的权限校验点已接入，但还没有角色分配入口 |

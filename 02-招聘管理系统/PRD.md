## 1. 背景与问题

### 1.1 用户

| 角色 | 关注什么 |
|---|---|
| 集团 HR | 全集团招聘进度、编制与预算是否超限 |
| 二级单位人事 | 提报计划、跟审批、维护候选人 |
| 评委 | 候选人评审 |
| 管理岗 | 流程是否卡住、谁该处理 |

### 1.2 现状痛点

| # | 痛点 | 现象 |
|---|---|---|
| 1 | **流程靠群聊和邮件推** | 谁审到哪一步、上次谁驳回、驳回意见是什么，全靠人记；有人休假或离职，流程就断 |
| 2 | **权限靠前端隐藏按钮** | 前端把按钮藏了，用户直接调接口就绕过，是**假权限** |
| 3 | **误删连带数据全没** | 招聘计划关联候选人、审批记录、归档文件，物理删除一次不可恢复 |
| 4 | **管控在出口不在入口** | 计划先批，批完才发现超编制 / 超预算，再回头撤，事后追责谁也说不清 |
| 5 | **出问题无法回溯** | "谁在什么时候对哪条数据做了什么"查不到 |

### 1.3 问题陈述

> **让流程不靠人记、权限不靠自觉、误删可撤回。**

## 2. 目标与成功指标

### 2.1 产品目标

1. **三级审批链固化进系统**并全程留痕：二级单位 → 集团 HR → 集团领导。
2. **权限校验全部放后端**：前端隐藏按钮不算权限。
3. **管控前置**：提交审批前校验编制与预算上限，超限直接阻断并给明细。
4. **三级软删除**：软删除 → 可恢复 → 确认移除，第三级有强制前置条件。
5. **全量操作审计**：操作人 / IP / 模块 / 业务编号 / 时间。

### 2.2 成功指标（含口径）

| 指标 | 口径定义 | 目标 |
|---|---|---|
| 审批留痕完整率 | 有完整操作人 + 时间 + 意见的审批节点数 / 总审批节点数 | 100% |
| 越权拦截率 | 只读账号发起的写请求中被 403 拒绝的比例 | 100%（注册页新建账号口径） |
| 超限阻断率 | 超编制 / 超预算的提交中被阻断的比例 | 100% |
| 误删可恢复率 | 从"已删除"区成功恢复的记录数 / 已删除记录数 | 100% |
| 审计覆盖率 | 被 AOP 记录的业务操作数 / 应记录操作数 | 100% |
| **反指标** | 不出现"删了才发现不能恢复" | 物理删除前强校验状态 |

## 3. 用户流程

### 3.1 招聘计划主流程

```
二级单位人事登录
  → 创建招聘计划（岗位 / 人数 / 预算 / 需求说明）
      └─ 提交前自动校验：本年度编制人数上限、预算上限
            ├─ 超限 → 直接阻断，并给出"超了多少、上限多少"明细
            └─ 通过 → 提交审批
  → 三级串行审批：二级单位 → 集团 HR → 集团领导
       每一步记录：操作人 / 时间 / 意见
       ├─ 驳回 → 退回发起人修改后重新提交（历史意见保留）
       └─ 通过 → 进入候选人管理
  → 候选人：简历导入（Excel）/ 字段维护 / 项目与工作经历 / 评委评审
  → 录用归档：文件上传 + 版本管理；消息通知（飞书推送，发送留日志）
```

### 3.2 删除与恢复流程

```
删除计划 → 软删除（进入"已删除"区，列表默认过滤）
   → 恢复（回到正常列表）
   → 确认移除（物理删除）
        └─ 前置条件：不是"已删除"状态 → 直接抛异常拒绝
```

### 3.3 异常分支

| 分支 | 触发 | 行为 |
|---|---|---|
| 只读账号发起写请求 | 拦截器 | 非 GET + readonly → **403** |
| 超编制 / 超预算 | 提交前校验 | 阻断并给可读明细 |
| 非"已删除"状态请求物理删除 | 状态机 | **抛异常拒绝**（不是提示） |
| 文件上传失败 / 版本冲突 | 文件模块 | 保留上一版本，给出原因 |
| 飞书推送失败 | 通知模块 | 记录失败原因，不阻塞主流程 |

## 4. 范围

### 4.1 本期做

| 模块 | 内容 |
|---|---|
| 招聘计划 | 创建 / 编辑 / 版本快照 / 提交审批 / 移入已删除 / 恢复 / 彻底移除 |
| 审批流转 | 三级串行审批、审批意见、全程留痕、退回与重新提交 |
| 候选人管理 | 简历导入与归档、字段维护、项目与工作经历、评委评审 |
| 编制预算 | 按 单位 + 年度 配置上限；提交前自动校验；超限阻断 |
| 组织架构 | 多级单位维护 |
| 权限 | 后端强制拦截；只读账号写操作 403 |
| 审计 | AOP 操作日志（操作人 / IP / 模块 / 时间） |
| 文件 | 上传 / 下载 / 版本管理 |
| 消息通知 | 飞书推送（审批通知、拟录用通知），每次发送写日志 |
| 交付 | Windows / Linux 双环境、Docker 离线部署、NSSM 服务注册 |

### 4.2 明确不做

| 不做 | 理由 |
|---|---|
| 不做并行审批 | 会引入"多人同时审同一单"的一致性问题；首版先保证流程确定 |
| 不做审批层级可视化配置 | 三级硬编码，先跑通共性流程 |
| 不做跨单位数据共享 | 权限边界优先 |

## 5. 功能需求

| 编号 | 功能 | 描述 | 异常分支 | 验收标准 |
|---|---|---|---|---|
| FR-01 | 计划编制 | 创建 / 编辑招聘计划，含岗位、人数、预算 | 字段非法 → 400 | 字段完整、可保存版本 |
| FR-02 | 计划版本快照 | 每次关键变更留一版 | — | 可追溯到修改前状态 |
| FR-03 | 编制预算校验 | 提交前校验单位 + 年度上限 | 超限 → 阻断 + 明细 | 超限提交无法进入审批 |
| FR-04 | 三级串行审批 | 二级单位 → 集团 HR → 集团领导 | 驳回 → 退回重新提交 | 每个节点有操作人 / 时间 / 意见 |
| FR-05 | 权限拦截 | `/api/**`：非 GET + readonly → 403；仅登录/注册/退出放行 | 未登录 → 拒绝 | 直接调接口也拿不到写权限 |
| FR-06 | 三级软删除 | 软删除 → 恢复 → 确认移除 | 非"已删除"状态物理删除 → 抛异常 | 列表默认过滤 `deleted` |
| FR-07 | 候选人管理 | 简历 Excel 导入、字段维护、经历维护 | 导入格式错 → 逐行报错 | 导入结果可核对 |
| FR-08 | 评委评审 | 评委打分与意见 | — | 评审记录留痕 |
| FR-09 | 组织架构 | 多级单位维护 | — | 计划可绑定单位 |
| FR-10 | 操作日志 | AOP 记录操作人 / IP / 模块 / 业务编号 / 时间 | 记录失败不阻塞业务 | 可回溯任意业务操作 |
| FR-11 | 文件版本 | 上传 / 下载 / 版本管理 | 冲突 → 保留旧版 | 可查历史版本 |
| FR-12 | 消息通知 | 飞书推送审批与录用通知 | 失败 → 记录原因 | 每次发送写日志 |

## 6. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 列表默认过滤 `deleted` 并分页；关联查询避免全表扫描 |
| 安全 | 权限校验全部在后端；写操作有明确角色约束 |
| 数据 | 关键业务表留版本快照；软删除不物理删除业务数据 |
| 可追溯 | 审批留痕 + AOP 日志构成完整可追溯链路 |
| 交付 | 支持 Windows / Linux 双环境；提供 Docker 离线部署与 NSSM 服务注册 |
| 可维护 | 数据库变更以 SQL 迁移脚本管理 |

## 8. 风险与依赖

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| 1 | 审批层级硬编码 | 不同单位可能需要不同层级 | 中期做成可配置 |
| 2 | 编制 / 预算**硬阻断**，无特批通道 | "确实需要超编"的场景走不通 | 补一条走更高层审批的特批通道 |
| 3 | 物理删除不级联 | 关联数据残留 | 严格做法应级联清理或归档 |
| 4 | 只读账号种子数据 role 值错误 | 该测试账号绕过拦截器 | **一行修复，已知未改**（见 §10） |
| 5 | 飞书 / 企微凭据 | 泄露风险 | 凭据不入库、不进公开仓库 |

## 9. 上线与灰度

| 阶段 | 内容 | 出口条件 |
|---|---|---|
| P0 | 计划 + 三级审批主流程 | 审批链路跑通并留痕 |
| P1 | 权限拦截 + 管控前置 | 只读账号 403；超限提交被阻断 |
| P2 | 软删除 + 审计 + 文件 + 通知 | 误删可恢复；操作可回溯 |
| P3 | Docker 离线部署 + NSSM 服务注册 | 目标环境可独立部署 |

## 10. 已知缺陷（不掩盖）

1. **权限模型四类设计、两类落地**：管理员与只读可用；招聘专员与评委的校验点已接入，但**缺角色分配入口**。
2. **种子账号 `role` 值写成 `user` 而不是 `readonly`**，导致该测试账号绕过只读拦截器（仅注册页新建账号被真正拦截）。
3. **表里有重复表**（`recruit_plan` / `recruitment_plan` 等）。
4. **审批层级硬编码**，不可配置。
5. **物理删除不级联**，只删主记录。
6. **无超编特批通道**，当前为硬阻断。

## 11. 后续迭代（按优先级）

| # | 迭代项 | 理由 |
|---|---|---|
| 1 | 修种子账号 role 值 | 一行修复，但直接影响"权限是否真生效"的可信度 |
| 2 | 补用户管理页与角色分配入口 | 让四类角色设计真正落地 |
| 3 | 审批层级可配置 | 适配不同单位 |
| 4 | 超编特批通道 | 管控与灵活性的平衡 |
| 5 | 物理删除级联或归档 | 数据一致性 |
| 6 | 清理重复表 | 降低维护成本 |

## 三处最值得看的实现

### 1 招聘计划状态机

```
draft → submitting → approved
         ↓              rejected → submitting（修改后重新提交）
    draft ──软删除──► deleted ──恢复──► draft
```

**关键防御**：更新计划时**刻意不覆盖 `status` 字段** —— 防止前端篡改状态绕过审批。

### 2 三级软删除

```
软删除 → 已删除区 → 确认移除
 可恢复    可恢复    不可恢复
```

**两个刻意的约束**：只有 `draft` 能删除；恢复后回到 `draft` 而不是原状态（**避免用"删掉→恢复"绕过审批**）。

### 3 权限用 HTTP 方法一刀切

只读拦截按 **HTTP 方法**判定，而不是逐个接口标注解。
**新增接口自动受保护**，不存在"忘记加注解"的漏洞。

## 我在这个项目上还没做到的

| # | 缺陷 | 影响 |
|---|---|---|
| **1** | **`init.sql` 里的只读种子账号 `role` 值是 `user`** | 只读拦截判断的是 `"readonly"`，**这个种子账号实际不被拦截** —— 根因是建表注释与注册逻辑对角色取值的定义不一致 |
| 2 | **经理 / 评委是死分支** | 权限校验点已接入，但没有角色分配入口 |
| 3 | **无单元测试** | 全靠手工验证 |
| 4 | `CandidateController` 563 行 | 偏胖，可按导入/查询/流转拆开 |
| 5 | 表名与实体名不一致 | SQL 是 `recruitment_plan`，实体是 `RecruitPlan` |

# 人力招聘归档系统 · 产品决策记录

> 记录**每个决策当时为什么这么定**，以及**代价是什么**。
> 设计文档讲"怎么实现"，这份讲"为什么这么设计"。

---

## 决策 1：用状态机而不是布尔标志

**问题**：招聘计划有「草稿 / 提交中 / 已通过 / 已驳回 / 已删除」多种状态。
最容易的写法是加几个布尔字段：`is_submitted` / `is_approved` / `is_deleted`。

**为什么不用布尔**：

| 布尔字段的问题 | 具体后果 |
|---|---|
| **组合爆炸** | 5 个布尔 = 32 种组合，其中大部分是无意义状态（如 `is_approved=true` 且 `is_deleted=true`） |
| **无法表达时序** | 「先通过再删除」和「先删除再提交」看起来一样 |
| **校验写不齐** | 每个接口都要重新判断一遍合法组合，容易漏 |

**采用方案**：单一 `status` 字段 + 显式流转规则。

**代价**：
- 每个操作入口都要写状态校验（`if (!"draft".equals(status)) throw ...`）
- 新增状态要改多处代码

**收益**：状态永远只有 6 种合法值，**不可能出现"已通过又已删除"这种矛盾状态**。

## 决策 2：状态字段绝不由前端写入

**问题**：更新计划时，前端会提交一个完整的计划对象。

**风险**：如果前端（或攻击者）把 `status` 字段改成 `approved` 一起提交，
**就绕过了整条审批链**。

**采用方案**：更新方法**刻意不覆盖 `status` 字段**。

```java
// RecruitPlanService.java:285
// 注意：不覆盖status字段，防止前端篡改状态绕过审批
```

**为什么这个决定重要**：审批流是企业系统的核心控制点。
**只要有一个入口能直接写状态，整套审批就形同虚设。**

**代价**：状态变更必须走专门的方法（`submit` / `revoke` / `approve` / `reject`），
不能顺手在通用 update 里改。

**收益**：**前端即使被篡改，也改不动状态。**

## 决策 3：三级软删除，而不是直接删

**问题**：招聘计划的误删成本很高（关联岗位、预算、审批记录）。

**三个可选方案**：

| 方案 | 问题 |
|---|---|
| 直接硬删除 | 误删无法恢复 |
| 只做软删除 | 无效数据永远堆在库里，列表越来越乱 |
| **三级删除** ✅ | —— |

**采用方案**：

```
软删除 → 已删除区 → 确认移除（真删）
  可恢复      可恢复      不可恢复
```

**两个刻意的约束**：

| 约束 | 理由 |
|---|---|
| **只有 `draft` 能软删除** | 已提交/已审批的计划有业务痕迹，不允许直接删 |
| **恢复后回到 `draft`，不是原状态** | 恢复后必须重新走审批，避免"删掉→恢复"来跳过审批 |

**代价**：用户理解成本高一点（要解释三个阶段）。

**收益**：**误删可救，且不能用来绕过审批。**

## 决策 4：审批链按单位层级自动决定

**问题**：集团总部和二级单位的审批链不一样。

**两个可选方案**：

| 方案 | 问题 |
|---|---|
| 让用户手选审批链 | 容易选错；每次都要选 |
| **按申报单位自动决定** ✅ | —— |

**采用方案**：

```java
// 集团总部：集团 HR 审批 → 集团领导审批（2 级）
// 二级单位：二级单位审批 → 集团 HR 审批 → 集团领导审批（3 级）
```

**关键细节**：审批链在**创建流程时一次性确定并落库**，而不是每次读取时重新计算。

**为什么**：如果单位层级后来调整了，
- 每次重算 → 历史流程的审批链也会跟着变，**已完成的审批记录会变得不可解释**
- 一次确定 → 历史流程保持原样

**收益**：**审批记录可追溯，不会因为组织架构调整而失真。**

## 决策 5：权限用 HTTP 方法一刀切，而不是逐个接口标注解

**问题**：只读账号要禁止所有写操作。常见做法是给每个接口加权限注解。

**为什么不用注解**：

| 注解方案的问题 | 后果 |
|---|---|
| **靠自觉** | 新增接口忘记加注解 → 权限漏了 |
| **容易不一致** | 有的接口用 `@PreAuthorize`，有的用自定义注解 |
| **难审计** | 要通读所有接口才知道权限覆盖情况 |

**采用方案**：用 `ReadonlyInterceptor` 按 **HTTP 方法**一刀切。

```java
// GET 一律放行
if ("GET".equalsIgnoreCase(method)) return true;

// readonly 角色的一切写操作（POST/PUT/DELETE）→ 403
if ("readonly".equals(user.getRole())) {
    response.setStatus(403);
    return false;
}
```

**收益**：**新增接口自动受保护**，不存在"忘记加注解"这种漏洞。

**代价**：粒度粗。如果将来出现"某个 POST 接口只读账号也该能用"，
需要往白名单里加。

**但这是个好的代价** —— 默认拒绝比默认允许安全。

## 决策 6：操作日志用 AOP 注解，而不是手写

**问题**：每个写操作都要记日志（谁、什么时候、做了什么）。

**两个可选方案**：

| 方案 | 问题 |
|---|---|
| 在 Service 里手写 `logService.record(...)` | 重复代码；忘写就漏 |
| **`@Log` 注解 + AOP 切面** ✅ | —— |

**采用方案**：

```java
@PostMapping("/{id}/restore")
@Log(module = "招聘计划", description = "恢复计划")   // ← 一行
public Map<String, Object> restorePlan(...)
```

**收益**：
- 控制器上**一行注解**，业务代码零侵入
- 想审计"哪些操作有日志"，搜 `@Log` 即可

**代价**：注解只能描述固定文案，无法记录动态内容（如"修改了哪几个字段"）。
本项目的做法是**用变更对比补上**：

```java
// RecruitPlanService.java:353
if (!Objects.equals(before.getStatus(), after.getStatus())) changes.add("状态");
```

## 决策 7：注册时只开放两个角色

**问题**：权限模型设计了 4 个角色（管理员 / 经理 / 评委 / 只读），
但经理和评委**没有分配入口**。

**采用方案**：`UserService.register()` 明确只接受两种：

```java
if (!"admin".equals(finalRole) && !"readonly".equals(finalRole)) {
    throw new RuntimeException("注册等级仅支持：管理员(admin) 或 只读(readonly)");
}
```

**为什么这么定**：
- 与其做一个**半成品**的角色管理界面，不如**明确只支持两种**
- 经理/评委的**权限校验点已经写好了**，只差分配入口 —— 将来补上即可

**这就是"宁可少做，不可做假"**：界面上不提供选择，就不会让用户以为能用。

**代价**：功能看起来比别人少。

**收益**：**用户不会遇到"选了经理却什么都不生效"的困惑。**

## 决策 8：编制预算在提交前校验，而不是提交后

**问题**：预算超了应该在哪个环节拦？

**两个可选方案**：

| 方案 | 后果 |
|---|---|
| 提交后由审批人发现 | 审批人要做数据核对工作，且退回后申请人已经白做一轮 |
| **提交时自动校验并阻断** ✅ | —— |

**采用方案**：提交审批前自动校验该单位本年度的：
- **编制人数上限**
- **预算上限**

超限则**阻断提交**，并给出**超了多少的明细**。

**收益**：**把校验前置到申请人这一环** —— 申请人当场就能改，不用等审批人退回。

**代价**：提交接口变慢（要查统计）。

---

## 决策 9：Excel 导入用监听器逐行处理

**问题**：候选人可能一次导入几百上千条。

**两个可选方案**：

| 方案 | 风险 |
|---|---|
| 一次性读入内存再处理 | 数据量大时 **OOM** |
| **监听器逐行处理** ✅ | —— |

**采用方案**：`CandidateExcelListener` + `CandidateImportRow`（EasyExcel 监听器模式）。

**收益**：内存占用与行数无关，**大批量导入不会拖垮服务**。

**代价**：无法做"全量校验后统一回滚"——只能逐行报错。

**这与业务匹配**：导入候选人时，**部分成功的价值大于全部失败**。

## 决策 10：通知失败不阻断主流程

**问题**：飞书通知发送失败时，要不要让整个操作回滚？

**采用方案**：**不阻断**。通知失败只记日志。

**理由**：

| 场景 | 应该怎样 |
|---|---|
| 审批通过 + 飞书发送失败 | **审批必须成功**（业务事实已成立），通知失败可补发 |
| 审批通过 + 因为通知失败而回滚 | ❌ 用户会看到"审批失败"，但实际审批已经过了 |

**收益**：**业务操作与通知解耦，通知是"尽力而为"，业务是"必须成功"。**

## 归纳：这套系统的四条设计原则

| 原则 | 体现 |
|---|---|
| **1. 默认拒绝** | 只读拦截按 HTTP 方法一刀切；新增接口自动受保护 |
| **2. 关键字段不可由外部写入** | `status` 不被 update 覆盖 |
| **3. 破坏性操作必须可逆或留痕** | 三级删除；操作日志 AOP |
| **4. 校验前置** | 预算超限在提交时拦，不等审批人发现 |

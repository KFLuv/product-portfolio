## 一、系统定位

## 三、招聘计划状态机

**这是整个系统的核心。** 状态流转写死在 Service 层，前端无法篡改。

```
                    ┌─────────┐
                    │  draft  │  草稿
                    └────┬────┘
              提交 │              │ 撤回
                    ▼              │
              ┌─────────────┐      │
              │ submitting  │ 提交中
              └──────┬──────┘      │
                     │             │
        ┌────────────┼─────────────┘
        │ 审批通过    │ 审批驳回
        ▼            ▼
   ┌──────────┐  ┌──────────┐
   │ approved │  │ rejected │ 已退回
   └──────────┘  └────┬─────┘
                      │ 修改后重新提交
                      ▼
                submitting

   draft ──(软删除)──► deleted ──(恢复)──► draft
```

**可编辑状态只有两个：`draft` 和 `rejected`。**

```java
// RecruitPlanService.java:247
String status = existing.getStatus();
if (!"draft".equals(status) && !"rejected".equals(status)) {
    throw new RuntimeException("仅草稿和已退回状态的计划可编辑，当前状态不允许修改");
}
```

### 关键防御：状态字段不可被前端覆盖

```java
// RecruitPlanService.java:285
// 注意：不覆盖 status 字段，防止前端篡改状态绕过审批
```

更新计划时**刻意不写 `status` 字段**。如果前端传 `status=approved` 过来，会被忽略。

## 四、三级软删除

**问题**：误删招聘计划会造成实际业务损失，但完全不做删除又无法清理无效数据。

**方案**：分三步，每一步都可逆或不留痕。

| 级别 | 操作 | 数据状态 | 能否恢复 |
|---|---|---|---|
| **1** | **软删除** | `status='deleted'`，数据仍在表里 | ✅ 可恢复 |
| **2** | **已删除区** | 列表默认不返回，仅 `status=deleted` 时返回 | ✅ 可恢复 |
| **3** | **确认移除** | 真正从数据库删除 | ❌ 不可恢复 |

```java
// RecruitPlanService.java:487 —— 仅草稿可移入已删除
if (!"draft".equals(plan.getStatus())) {
    throw new RuntimeException("仅草稿状态的计划可移入已删除区");
}
plan.setStatus("deleted");
```

```java
// RecruitPlanService.java:500 —— 恢复：回到草稿
public void restorePlan(Long id) {
    // 仅已删除状态的计划可恢复
    ...
}
```

### 两个刻意的约束

| 约束 | 理由 |
|---|---|
| **只有 `draft` 能软删除** | 已提交/已审批的计划有业务痕迹，不允许直接删 |
| **恢复后回到 `draft` 而不是原状态** | 恢复后必须重新走一遍审批流程，避免绕过 |

**列表过滤逻辑**：

```java
// RecruitPlanService.java:133
// 已删除的计划只在显式查询 status=deleted 时返回
if ("deleted".equals(status)) return "deleted".equals(plan.getStatus());
return !"deleted".equals(plan.getStatus());
```

## 五、多级审批链

**按申报单位的层级自动决定审批链路** —— 不需要用户手动选。

```java
// ProcessApprovalService.java
/** 审批节点配置 —— 按单位层级决定审批链路 */
private static final Map<Long, String[]> APPROVAL_NODES = new HashMap<>();
static {
    // 集团总部：集团 HR 审批 → 集团领导审批
    APPROVAL_NODES.put(1L, new String[]{"集团 HR 审批", "集团领导审批"});
    // 二级单位：二级单位审批 → 集团 HR 审批 → 集团领导审批
    APPROVAL_NODES.put(2L, new String[]{"二级单位审批", "集团 HR 审批", "集团领导审批"});
    APPROVAL_NODES.put(3L, new String[]{"二级单位审批", "集团 HR 审批", "集团领导审批"});
}
```

```
集团总部（orgUnitId=1）      二级单位（orgUnitId=2/3）
      集团 HR 审批                 二级单位审批
           ↓                              ↓
      集团领导审批                  集团 HR 审批
                                          ↓
                                    集团领导审批
```

**三条流程类型**：`recruit_plan`（招聘计划）· `position`（岗位）· `candidate`（候选人）

**三种状态**：`pending` 待处理 · `approved` 已通过 · `rejected` 已驳回

**设计要点**：审批链在**创建流程时一次性确定**并写入 `approval_nodes` 字段（逗号分隔），
而不是每次读取时重新计算 —— 避免单位层级调整后历史流程的审批链发生变化。

## 六、权限模型

### 三层防御

| 层 | 组件 | 职责 |
|---|---|---|
| **1** | `AuthFilter` | 未登录一律 401，放行白名单路径 |
| **2** | `ReadonlyInterceptor` | `readonly` 角色全局禁止写操作 |
| **3** | `PermissionUtil` | 业务方法内校验具体角色 |

### 角色定义

| 角色 | 说明 | 实际可用 |
|---|---|---|
| `admin` | 管理员 | ✅ **可注册** |
| `manager` | 经理 | ⚠️ **权限校验点已接入，但无角色分配入口** |
| `judge` | 评委 | ⚠️ 同上 |
| `readonly` | 只读 | ✅ **可注册** |

**注册入口只接受两种角色：**

```java
// UserService.register()
if (!"admin".equals(finalRole) && !"readonly".equals(finalRole)) {
    throw new RuntimeException("注册等级仅支持：管理员(admin) 或 只读(readonly)");
}
```

### 只读拦截实现

```java
// ReadonlyInterceptor.java
// GET 查询一律放行
if ("GET".equalsIgnoreCase(method)) return true;

// 认证白名单放行（登录/注册/退出必须能用）
for (String allowPath : ALLOW_WRITE_PATHS) {
    if (uri.equals(allowPath)) return true;
}

// readonly 角色的一切写操作 → 403
if (user != null && "readonly".equals(user.getRole())) {
    response.setStatus(403);
    response.getWriter().write("{\"success\":false,\"message\":\"只读账号无操作权限，仅可查看\"}");
    return false;
}
```

> **这个设计比"给每个接口标权限注解"更硬**：它按 HTTP 方法一刀切，
> **新增接口自动受保护**，不会因为忘记加注解而漏掉。

### 必须说清的缺陷

| # | 缺陷 | 后果 |
|---|---|---|
| **1** | **`init.sql` 里的只读种子账号 `role` 值是 `user`** | `ReadonlyInterceptor` 判断的是 `"readonly".equals(role)`，**这个种子账号实际上不被拦截** |
| **2** | 只有通过注册接口创建的账号才是真正的 `readonly` | 种子数据与注册逻辑不一致 |

**根因**：`init.sql` 的建表注释写「角色：admin 或 user」，而注册逻辑写的是 `admin` / `readonly`
—— **两处对角色取值的定义不一致**，种子数据按旧定义写成了 `user`。

## 十一、已知技术债

| # | 技术债 | 建议 |
|---|---|---|
| 1 | **只读种子账号 `role` 值与注册逻辑不一致** | `init.sql` 改成 `readonly` |
| 2 | **`manager` / `judge` 是死分支** | 权限校验点已接入但无分配入口，需补角色管理 |

| 5 | `CandidateController` 563 行 | 偏胖，可按导入 / 查询 / 流转拆开 |
| 6 | 表名与实体名不一致 | SQL 是 `recruitment_plan`，实体是 `RecruitPlan`，Repository 方法名易混淆 |

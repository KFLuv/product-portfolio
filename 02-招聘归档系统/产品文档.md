# 人力招聘全流程数字化归档管理系统 · 产品文档

> **产品定位**：覆盖招聘计划 → 审批流转 → 候选人管理 → 录用归档全流程的多级组织管理系统
> **我的角色**：需求设计 · 功能验收（自有项目）
> **源码**：https://github.com/KFLuv/recruit-system
> **状态**：✅ 已完成并交付

---

## 一句话

**让流程不靠人记、权限不靠自觉、误删可撤回。**

---

## 目标用户与场景

| | |
|---|---|
| **用户** | 集团 HR、二级单位人事、评委、管理岗 |
| **场景** | 多级组织下的招聘全流程（计划编制 → 三级审批 → 候选人管理 → 录用归档） |
| **核心痛点** | ① 流程靠群聊和邮件推，**断了不知道断在谁那里** ② 权限靠前端隐藏按钮，**调接口就绕过** ③ 误删连带数据全没，**不可恢复** |

---

## 核心产品决策

> 每条都是 **约束 → 选择 → 理由**。

### 决策 1 · 把三级审批链固化进系统，并全程留痕

| | |
|---|---|
| **约束** | 线下审批靠群聊翻记录；谁审到哪一步、上次谁驳回、驳回意见是什么，**全靠人记**。一旦有人休假或离职，流程就断 |
| **选择** | 三级审批链固化进系统：**二级单位 → 集团 HR → 集团领导**；每一步谁审的、什么时候审的、什么意见，**全部落库留痕** |
| **理由** | **流程断了要能查是断在谁那里** —— 这是"流程不靠人记"的落地 |
| **代价** | 目前是**串行**审批，一级过了一级才能审。并行审批会引入"多人同时审同一单"的一致性问题，首版选择先保证流程确定 |

### 决策 2 · 权限模型：四类角色设计、两类落地

| | |
|---|---|
| **约束** | 不同岗位看到的和能做的不同；但前端隐藏按钮是**假权限**，用户直接调接口就绕过去了 |
| **选择** | 按**管理员 / 招聘专员 / 评委 / 只读**四类角色设计权限模型；**权限校验点全部放在后端** |
| **理由** | **权限校验必须在后端，这是原则问题**，不是界面问题 |
| **落地情况** | ⚠️ **实际落地并跑通的是「管理员」与「只读」两类**（注册接口只放这两类）；招聘专员与评委的**权限校验点已接入**，但**还没有角色分配入口** |

**只读账号的拦截实现（这是本决策的核心价值）：**

| | |
|---|---|
| **一般做法** | 前端把按钮隐藏掉 —— **这是假的权限** |
| **我的做法** | 后端拦截器注册到 `/api/**`：**非 GET 请求 + 当前用户是只读 → 直接返回 403**，仅登录/注册/退出三个接口放行 |
| **效果** | 用户即使直接调接口，也拿不到写权限 |

> **⚠️ 已知缺陷**：数据库种子账号的 `role` 值写成了 `user` 而不是 `readonly`，导致**该测试账号绕过拦截器**。只有通过注册页新建的账号才真正被拦截。**这是一个我需要修的 bug。**

### 决策 3 · 管控前置：把校验放在流程入口，而不是出口

| | |
|---|---|
| **约束** | 原来的做法是：计划先批 → 批完发现超编制或超预算 → 再回头撤。**事后追责，谁也说不清** |
| **选择** | 提交审批**前**自动校验该单位本年度的**编制人数上限**与**预算上限**；超限**直接阻断提交**，并给出明细（超了多少、上限多少） |
| **理由** | **管控规则放在流程入口，而不是流程出口** —— 这是这个设计唯一的价值点 |
| **代价** | 目前是**硬阻断**。合理做法是加一条"特批通道"（走更高层审批），**这是可以补的** |

### 决策 4 · 三级软删除：让误删可撤回

| | |
|---|---|
| **约束** | 招聘计划关联着**候选人、审批记录、归档文件**。物理删除一次，**连带数据一起消失，且不可恢复** |
| **选择** | 三级状态机：**软删除**（进已删除区）→ **可恢复** → **确认移除**才物理删除 |
| **理由** | **误删一次，连带数据全没了** —— 所以删除必须可撤回 |
| **关键设计** | **第三级有强制前置条件**：不是"已删除"状态的计划，**直接抛异常拒绝物理删除**。不是"提示一下"，是**真的拒绝** |
| **代价** | 列表查询必须默认过滤 `deleted` 状态，只有显式查询才返回已删除区；物理删除时**关联数据目前只删主记录**，严格做法应级联清理或归档 |

### 决策 5 · AOP 操作日志审计

| | |
|---|---|
| **约束** | 出问题时需要能回溯"谁在什么时候对哪条数据做了什么" |
| **选择** | 通过 AOP 统一记录：操作人、IP、模块、操作描述、业务编号、操作时间 |
| **理由** | 与三级审批留痕配合，构成完整的**可追溯链路** |

## 系统规模

| 项 | 值 |
|---|---|
| 后端 Controller | **16 个** |
| 数据表 | **16 张**（JPA 实体 16 个；`database/init.sql` 里有 9 张建表语句，其余由 `ddl-auto=update` 自动建） |
| 数据库脚本 | 12 个 SQL 文件（含多次迁移） |
| 技术栈 | Java 11 · Spring Boot · Spring Data JPA · MySQL · AOP / Vue 3 · Element Plus · Pinia |

> **如实说明**：16 张表里包含**历史遗留的重复表**（如 `recruit_plan` 与 `recruitment_plan`），是我迭代过程中没清理干净的；16 个 Controller 里也包含 `FeishuTestController`、`BugReportController` 等工具类，**不全是业务模块**。

## 功能范围

| 模块 | 内容 |
|---|---|
| **招聘计划** | 创建、编辑、版本快照、提交审批、移入已删除、恢复、彻底移除 |
| **审批流转** | 三级串行审批、审批意见、全程留痕、退回与重新提交 |
| **候选人管理** | 简历管理与归档、候选人字段维护、项目/工作经历、评委评审 |
| **编制预算** | 按单位+年度配置上限、提交前自动校验、超限阻断 |
| **组织架构** | 多级单位维护 |
| **权限** | 后端强制拦截、只读账号写操作 403 |
| **审计** | AOP 操作日志、操作人/IP/模块/时间 |
| **文件** | 上传、下载、版本管理 |
| **消息通知** | 飞书推送（审批通知、拟录用通知），每次发送写日志 |
| **交付** | Windows / Linux 双环境、Docker 离线部署、NSSM 服务注册 |

## 我在这个产品上还没做到的

| # | 缺什么 | 说明 |
|---|---|---|
| **1** | **权限模型四类设计、两类落地** | 管理员与只读可用；**招聘专员与评委没有角色分配入口** —— 需要一个用户管理页让管理员分配角色 |
| **2** | **种子账号 role 值有 bug** | `readonly` 测试账号的 role 写成了 `user`，**绕过了只读拦截器**。一行修复，但我还没改 |
| **3** | **表里有重复表** | `recruit_plan` / `recruitment_plan`、`plan_version` / `recruitment_plan_version` —— 迭代遗留，没清理 |
| **4** | **审批层级硬编码** | 三级不可配置。不同单位可能需要不同层级，应该做成可配置 |
| **5** | **物理删除不级联** | 目前只删主记录，严格做法应级联清理或归档 |
| **6** | **无超编特批通道** | 现在是硬阻断，缺少"确实需要超编"的合规路径 |

## 第一章 设计目标与约束

### 1.1 设计目标

| # | 目标 | 落地方式 |
|---|---|---|
| 1 | **AI 回答要像旅行顾问，不像通用百科** | `SYSTEM_PROMPT` 限定角色与输出结构 |
| 2 | **AI 产出要能留存** | 新增行程本（保存 / 列表 / 查看 / 删除） |
| 3 | **外部服务不可靠时仍可用** | 配置校验 + 本地兜底 + 异常降级 |
| 4 | **不被单一模型厂商锁定** | 只读三项配置，换厂商改三行 |
| 5 | **用户数据不可越权访问** | 所有行程接口按 `username` 限定 |

### 1.2 设计约束

| 约束 | 来源 | 影响 |
|---|---|---|
| **课程要求用 Maven + JavaWeb 项目** | 课程 | 必须打成可执行 jar，不依赖外部 Tomcat |
| **课程要求原生 HTML/CSS/JS** | 课程 | **零构建工具**，前端直接放 `resources/static` |
| **演示环境可能没有 API Key** | 现实 | **必须有兜底路径**，否则功能直接挂 |
| **评审是一次性的** | 现实 | 启动要简单，不能要求复杂部署 |

## 第三章 核心流程设计

### 3.1 AI 对话流程

```
用户输入
   │
   ▼
读配置（ai.base-url / api-key / model）
   │
   ▼
三项都填了吗？ ──否──► 返回本地兜底模板（功能不挂）
   │是
   ▼
拼请求体：{ model, temperature, messages:[system, user] }
   │
   ▼
POST {base-url}/chat/completions
   Authorization: Bearer {api-key}
   │
   ▼
HTTP 200 吗？ ──否──► 抛异常 → Controller catch → 返回友好提示
   │是
   ▼
取 choices[0].message.content
   │
   ▼
内容为空吗？ ──是──► 抛异常 → 同上
   │否
   ▼
返回纯文本给前端
```

### 3.2 行程本流程（我新增）

**保存：**
```
用户点"保存行程"
   │
   ▼
登录了吗？ ──否──► "请先登录后再使用行程本"
   │是
   ▼
正文为空吗？ ──是──► "行程内容为空，无法保存"
   │否
   ▼
标题为空？ ──是──► 命名"未命名行程"
标题超 120 字？ ──是──► 截断到 120
   │
   ▼
insert into trip(username, title, content, create_time)
   ★ username 来自 session，不接受前端传入
```

**查看 / 删除（越权防护关键）：**
```
用户请求 id=5 的行程
   │
   ▼
从 session 取 username（不接受前端传）
   │
   ▼
select ... from trip where id = 5 and username = 当前用户
                        └──────────★ 双条件 ──────────┘
   │
   ├─ 查到 → 返回
   └─ 查不到 → "行程不存在"
              （别人的行程在这里被拦住，且不暴露"存在但无权"）
```

> **为什么不用"先查再判断归属"两步？**
> 双条件一次查询**更简单，也不会因为忘记判断归属而出错**。

## 第四章 关键设计决策

### 4.1 为什么用 OpenAI 兼容协议

| | |
|---|---|
| **问题** | 各家大模型 API 协议不同，写死一家就被锁定 |
| **选择** | 走 `chat/completions` 这套**事实标准** |
| **收益** | 智谱、讯飞星火、硅基流动、阿里百炼、DeepSeek、Groq **全部兼容** |

**配置写法：**

```properties
server.port=8078
server.servlet.context-path=/chat

# 换厂商只改这三行
ai.base-url=https://api.deepseek.com
ai.api-key=
ai.model=deepseek-flash
```

> **`base-url` 填到域名级即可**，代码用 `stripTrailingSlash()` 处理尾部斜杠，再自动补 `/chat/completions`。
> **少填一个字段就少一个出错点。**

### 4.2 为什么必须有兜底

| 场景 | 不做兜底的后果 |
|---|---|
| 没配 API Key | **整个 AI 功能挂掉，演示失败** |
| Key 欠费 | 接口 500 |
| 网络不通 | 接口 500 |
| 模型返回空内容 | 前端显示空白 |

**兜底设计：**

```java
public boolean isConfigured() {
    return !isBlank(baseUrl) && !isBlank(apiKey) && !isBlank(model);
}
```

```java
if (aiChatService.isConfigured()) {
    try {
        return aiChatService.chat(message);
    } catch (Exception e) {
        log.error("调用 AI 接口失败", e);
        return "抱歉，AI 服务暂时不可用：" + e.getMessage();
    }
}
return "感谢您的咨询！关于" + userMessage + "，我建议您可以考虑以下行程：\n\n...";
```

> **原则:产品的可用性不能建立在"外部服务一定正常"上。**

### 4.3 人设提示词的设计

```java
private static final String SYSTEM_PROMPT =
        "你是「旅行助手」，一位专业的中文旅行规划顾问。"
                + "请用中文回答，语气亲切专业，条理清晰。"
                + "涉及行程时按天给出安排，并适当给出交通、美食、注意事项方面的建议。"
                + "如果用户的问题与旅游无关，也可以正常回答，但要简短。";
```

| 这句话 | 作用 |
|---|---|
| "专业的中文旅行规划顾问" | **定角色** —— 不是通用助手 |
| "按天给出安排" | **定输出结构** —— 不是一段散文 |
| "适当给出交通、美食、注意事项建议" | **定内容维度** |
| "与旅游无关也可以回答，**但要简短**" | **既不硬拒答（体验差），也不跑偏（丢定位）** |

### 4.4 密码修改的三道校验

```java
// 1. 校验当前密码 —— 防止别人拿到页面就能改密码
if (!Objects.equals(currentPassword,
        queryString("select password from user where username = ?", username))) {
    return fail(result, "当前密码不正确");
}

// 2. 要改密码时，两次输入必须一致
if (changePassword && !Objects.equals(newPassword, confirmPassword)) {
    return fail(result, "新密码和确认密码不匹配");
}
if (!changePassword && !changeEmail) {
    return fail(result, "没有需要修改的内容");
}

// 3. 真正落库（? 占位符，防 SQL 注入）
MySQLUtil.executeUpdate("update user set password = ? where username = ?", newPassword, username);
```

> **改造前这里只比了两次密码是否一致就返回"成功"，一个字都没落库。**

## 第五章 接口设计

### 5.1 接口清单

| 方法 | 路径 | 作用 | 是否需登录 |
|---|---|---|---|
| POST | `/login` | 登录，写 session（key=`loginUser`） | — |
| POST | `/reg` | 注册（查重后入库） | — |
| GET | `/captcha` | 图形验证码（JDK AWT 画图，无三方依赖） | — |
| POST | `/Aichat` | **AI 对话** | 否 |
| POST | `/myinfo` | 当前用户信息 | 否（返回 `login=false`） |
| POST | `/updateUserInfo` | 改密码 / 邮箱 | **是** |
| POST | `/destinations` | 目的地搜索 | 否 |
| POST | `/trips/save` | 行程保存 | **是** |
| POST | `/trips/list` | 行程列表 | **是** |
| POST | `/trips/get` | 行程详情 | **是** |
| POST | `/trips/delete` | 行程删除 | **是** |

### 5.2 关键接口的响应结构

**`POST /myinfo`（未登录也返回 200）：**

```json
{ "login": "false", "name": "", "email": "" }
```

> **为什么不返回 401？**
> 原注释写得很清楚:*"没登录也返回 200，让前端自己决定怎么提示，不至于控制台一片红。"*
> **这是前端体验的取舍** —— 未登录是正常状态，不该在控制台报错。

**`POST /trips/list`：**

```json
{
  "status": "success",
  "trips": [
    { "id": 12, "title": "三亚 5 天亲子游", "createTime": "2026-05-12 14:30" }
  ]
}
```

> **注意:列表不返回 `content`** —— 正文可能很长，列表页只要标题和时间。

**`POST /trips/get`（失败示例）：**

```json
{ "status": "error", "message": "行程不存在" }
```

> **别人的行程、不存在的行程，返回同一句话** —— 不暴露"存在但无权"这个信息。

### 5.3 参数校验与安全

| 校验点 | 规则 | 目的 |
|---|---|---|
| 用户名唯一 | 注册前查重 | 防重复注册 |
| 当前密码 | 改密码前必须匹配 | 防他人改密 |
| 行程正文 | 空则拒绝保存 | 防脏数据 |
| 行程标题 | 空则默认 / 超 120 字截断 | 防超长 |
| **数据归属** | `username` 只从 session 取 | **防越权** |
| **SQL** | 全部用 `?` 占位符 | **防注入** |

## 第六章 数据设计

### 6.1 用户表 `user`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | int | 主键，自增 |
| `username` | varchar | 用户名（唯一） |
| `password` | varchar | 密码 |
| `email` | varchar | 邮箱 |

> ⚠️ **已知缺陷：密码明文存储。** 应改为 BCrypt 哈希。
> 课程要求是"加密写入"，我做的是简单编码，**强度不够**。

### 6.2 行程表 `trip`（我新增）

```sql
create table trip (
    id          int auto_increment primary key,
    username    varchar(64)  not null,   -- ★ 归属人
    title       varchar(120) not null,   -- 标题（超长自动截断）
    content     text         not null,   -- 正文
    create_time datetime     not null,
    index idx_user (username)            -- ★ 按用户查是最高频操作
);
```

**设计说明：**

| 设计 | 理由 |
|---|---|
| `username` 而非 `user_id` | 与现有代码的 session 取值方式一致（session 里存的是用户名） |
| `title` 限 120 字 | 超出在应用层截断，**避免插入报错** |
| `index idx_user` | 列表和查看都按 `username` 过滤，**最高频查询走索引** |
| `content` 用 `text` | 行程正文可能很长 |

### 6.3 景点表 `spot`

| 字段 | 说明 |
|---|---|
| `name` | 景点名 |
| `city` | 所在城市 |
| `category` | 分类（山水自然 / 滨海度假 / 历史文化 / 都市旅行 / 主题线路 / 海外旅行） |
| `keywords` | 关键词（用于模糊搜索） |
| `description` | 描述 |

**搜索逻辑：**

```sql
select name, city, category, description from spot
 where name like ? or city like ? or keywords like ?
```

> **三个字段同时模糊匹配** —— 用户输入"三亚"能命中城市，输入"滨海"能命中分类，输入"故宫"能命中名称。

## 第八章 我对 Agent 的接入设计（方案已完成，代码未实现）

> **诚实说明:本章只是设计，还没写代码。**

### 8.1 判断标准：LLM 调用 ≠ Agent

| 对比项 | 普通 LLM 调用（现状） | Agent |
|---|---|---|
| 输入 | 一句话 | 一句话 + 一组可调用的**工具** |
| 模型能做什么 | 只能"说" | 能"**决定去做什么**"，然后真的去做 |
| 是否读数据库 | 不能 | 能（通过工具） |
| 是否多轮 | 一问一答 | **循环**：想 → 调工具 → 看结果 → 再想 |
| 是否记上下文 | 无 | 有（Memory） |

**公式：**

```
Agent = LLM（大脑） + Tools（手脚） + Loop（循环） + Memory（记忆）
```

> **分水岭就是 Tools / Function Calling。**

### 8.2 四步接入方案

| 步 | 做什么 | 关键点 |
|---|---|---|
| **1** | 封装工具 | `searchDestination` / `saveTrip` / `listTrips` —— **全部复用已有代码，不重写** |
| **2** | 请求带 `tools` | JSON Schema 描述 + `tool_choice: auto` |
| **3** | 写 Agent 循环 | 模型有 `tool_calls` 就执行 → 结果塞回 `messages` → 再问（**`MAX_ROUNDS = 5`**） |
| **4** | 暴露接口 | `POST /agent/chat`，前端只改一个 URL |

**Agent 循环示意：**

```
用户提问
   │
   ▼
┌────────────────────────┐
│ 问模型（带上工具清单）    │◄─────────────┐
└───────────┬────────────┘              │
            ▼                           │
     模型要调工具吗？                     │
      │是              │否               │
      ▼                ▼                │
 执行 Java 工具    返回文字答案           │
      │              （结束）            │
      └── 结果塞回 messages ─────────────┘
```

### 8.3 八条踩坑清单

| # | 坑 | 后果 |
|---|---|---|
| 1 | **必须设 `MAX_ROUNDS`** | 反复调工具 → **一直循环、一直扣钱** |
| 2 | **工具执行必须 try-catch** | 把错误当工具结果返回，**模型能自己纠正**；否则接口 500 |
| 3 | **`arguments` 是字符串** | 必须再 `readTree()` 解析一次 |
| 4 | **`tool_call_id` 必须回填** | 与模型给的 `id` 不一致 → **厂商报 400** |
| 5 | **越权防护** | `username` 必须后端从 session 取，**绝不能让模型或前端传** |
| 6 | **成本与延迟** | 带工具请求更慢更贵，**能一次问完的别用 Agent** |
| 7 | **超时** | Agent 总耗时是各轮之和，前端要提示"可能需要几十秒" |
| 8 | **配置为空要兜底** | 缺任何一项走本地模板 |

> 完整方案见 [`源码/docs/技术提炼.md`](源码/docs/技术提炼.md)。

## 第九章 已知缺陷与技术债

| # | 缺陷 | 影响 | 建议 |
|---|---|---|---|
| 1 | **密码明文存储** | 数据泄露即明文 | 改 BCrypt |
| 2 | **数据库凭据硬编码** | 换环境要改代码 | 移到配置文件 / 环境变量 |
| 3 | **无连接池、无 ORM** | 每次新建连接，并发会成瓶颈 | 引入 HikariCP |
| 4 | **无多轮上下文** | 一问一答，不记得上一句 | `messages` 存 session（方案已有） |
| 5 | **无单元测试** | 全靠手工验证 | 至少覆盖登录/注册/行程 CRUD |
| 6 | **`webapp/` 有旧版残留** | 还硬编码 `localhost:8081` | 清理或标注为改造前存档 |
| 7 | **端口与课程要求不一致** | 要求 8081，实际 8078 | 对齐或写清说明 |
| 8 | **前端存在两份 `chat.html`** | `static/`（新，相对路径）与 `webapp/`（旧，绝对路径）并存 | 保留 `static/`，`webapp/` 归档 |

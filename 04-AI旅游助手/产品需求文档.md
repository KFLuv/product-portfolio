# AI 旅游助手 · 产品需求文档（PRD）

> **产品定位**：一个能对话规划行程、并把方案存下来的 AI 旅游助手
> **项目性质**：课程项目（《数字系统开发技术与应用》期末考查）+ **我的改造**
> **我的角色**：**在课程基础版本之上，接入真实大模型 + 新增「行程本」+ 修复 4 个缺陷**
> **状态**：✅ 可运行（Spring Boot 可执行 jar）
>
> **改造明细另见** [`改造报告.md`](改造报告.md)，技术设计见 [`设计文档.md`](设计文档.md)

## 一、产品概述

### 1.1 一句话

**输入你想去哪、想怎么玩，AI 给出行程规划，一键存进行程本。**

### 1.2 要解决什么问题

| 问题 | 现状 |
|---|---|
| **信息过载** | 面对海量旅游信息，游客要花大量时间筛选整理才能规划出满意方案 |
| **需求个性化** | 家庭游、蜜月游、美食之旅需求各不相同，**传统指南和旅行社服务难以覆盖** |
| **规划耗时** | 从"想去某地"到"有一份能执行的行程"，中间要查很多东西 |

### 1.3 产品定位

> **不是旅游攻略站，是"帮你把想去变成能去"的对话式规划助手。**

**和通用 AI 聊天的区别（这是核心定位）：**

| | 通用 AI | AI 旅游助手 |
|---|---|---|
| 回答风格 | 通用百科式 | **专业旅行顾问人设**，按天给安排 |
| 输出结构 | 一段话 | **按天 + 交通/美食/注意事项建议** |
| **结果留存** | 聊完就丢 | **可存进行程本，随时翻看** |
| 无关问题 | 正常回答 | 正常回答，**但刻意简短**（聚焦定位） |

> **"能存下来"是它区别于"随便找个 AI 聊"的关键** ——
> 一个只会聊天、不留痕迹的助手，**用第二次就要重新问一遍**。

## 四、核心产品决策

> 每条都是 **约束 → 选择 → 理由**。

### 决策 1 · AI 回答必须带"人设"，不能是通用百科

| | |
|---|---|
| **约束** | 直接问大模型"推荐个行程"，会得到一篇通用攻略，**和其他 AI 没有区别** |
| **选择** | 用 `SYSTEM_PROMPT` 限定角色与输出结构 |
| **理由** | **产品定位要靠提示词守住** —— 否则"旅游助手"就退化成一个贴了旅游名字的聊天框 |
| **具体做法** | 限定"专业的中文旅行规划顾问" + "涉及行程按天给出安排" + "适当给出交通、美食、注意事项建议" + "**与旅游无关的问题也可以回答，但要简短**" |

> **最后那条是我特意加的**：既不让它硬拒答（**体验差**），也不让它跑偏成通用百科（**丢定位**）。

### 决策 2 · 必须默认可用，不能依赖配置

| | |
|---|---|
| **约束** | API Key 可能没配、可能欠费、可能网络不通 —— **但演示/评审时功能不能挂** |
| **选择** | `isConfigured()` 检查三项配置：**缺任何一项就走本地模板回复**；调用异常返回友好提示 |
| **理由** | **产品的可用性不能建立在"外部服务一定正常"上** |
| **代价** | 未配置时回答质量明显下降，但**功能链路完整、可演示** |

### 决策 3 · 换大模型厂商只改三行

| | |
|---|---|
| **约束** | 各家 API 协议不同，**写死一家就被锁定** —— 涨价、限流、停服都动不了 |
| **选择** | 只读 `ai.base-url` / `ai.api-key` / `ai.model` 三项；`base-url` 填到域名级，**代码自动补 `/chat/completions`** |
| **理由** | 智谱、讯飞星火、硅基流动、阿里百炼、DeepSeek、Groq **都兼容 OpenAI 的 `chat/completions` 协议** |
| **收益** | 换厂商成本从"改代码"降到"改配置" |

### 决策 4 · 新增「行程本」，让 AI 的产出可留存 ⭐

| | |
|---|---|
| **约束** | 课程只要求"聊天问答"。但**聊完就丢** —— 用户下次还要重新问一遍 |
| **选择** | 新增行程本：保存 / 列表 / 查看 / 删除 |
| **理由** | **AI 给的建议如果不存下来，第二次就要重新问** —— 这是"助手"和"聊天框"的区别 |
| **代价** | 增加了数据库表、4 个接口和一套前端界面；**但这是我认为最值得加的功能** |

**接口设计的两个取舍：**

| 取舍 | 理由 |
|---|---|
| **列表不返回正文** | 正文可能很长，列表页只要标题和时间 —— **减少传输量、加快加载** |
| **未登录直接拒绝** | 不给匿名用户存数据的可能 |

### 决策 5 · 权限校验做在每条数据上，不是入口上

| | |
|---|---|
| **约束** | 行程按 `id` 查 —— **改个 id 就能看别人的行程** |
| **选择** | 保存 / 列表 / 查看 / 删除**四个接口全部按 `username` 限定**；`username` 只从后端 session 取 |
| **理由** | **权限只做在入口上是假的** —— 拿到 id 就能绕过 |
| **具体做法** | `where id = ? and username = ?`；删除失败明确返回"不存在或已被删除" |

### 决策 6 · 修改密码必须先验证当前密码

| | |
|---|---|
| **约束** | 改造前**只比两次新密码一致就返回成功**（而且一个字都没落库） |
| **选择** | ① 验当前密码 → ② 校验两次新密码一致 → ③ 真正 UPDATE |
| **理由** | **防止别人拿到页面就能改密码**；同时**"返回成功"必须等于"真的改成功"** |
| **额外** | SQL 全部用 `?` 占位符，**不用字符串拼接**（防注入） |

## 五、首版明确不做

| 不做 | 理由 |
|---|---|
| ❌ **不做机票/酒店预订** | 那是交易环节，涉及支付、退改、供应商对接，**和"规划助手"是两件事** |
| ❌ **不做用户游记/UGC 社区** | 会变成内容平台，**稀释"帮你做规划"的定位** |
| ❌ **不做社交分享** | 首版用户只服务自己 |
| ❌ **不接入 MCP** | 只有 3 个工具且在自建库里，**直接写方法更简单**（超过 10 个或要接第三方工具再上） |
| ❌ **不做 Agent（首版）** | 课程范围是"LLM 调用"。**Agent 循环我写了完整方案，但没实现** |
| ❌ **不做多语言** | 课程场景是中文用户 |

## 六、技术实现概览

| 层 | 选型 |
|---|---|
| 框架 | **Spring Boot 2.7.18**（内嵌 Tomcat，打成可执行 jar） |
| Java | 11 |
| 数据库 | MySQL 8 |
| 数据访问 | **原生 JDBC**（`util.MySQLUtil`，无连接池、无 ORM） |
| 前端 | 原生 HTML + CSS + JS + `fetch`，**零构建工具** |
| AI 调用 | JDK 自带 `java.net.http.HttpClient` + Jackson 拼 JSON |

**分层结构：**

```
controller/    表现层：只负责收参数、返回结果
  ├── LoginController / RegController    登录、注册
  ├── ChatController                     AI 对话、当前用户、改资料
  ├── TripController                     行程本增删查
  ├── DestinationController              目的地搜索
  └── CaptchaController                  图形验证码
service/
  └── AiChatService                      ★ 调用大模型的地方
util/
  └── MySQLUtil                          JDBC 工具
```

**调用链：**

```
前端 fetch → Controller → Service / MySQLUtil → 数据库或大模型 → 返回 JSON / 文本
```

## 八、数据设计

### 8.1 用户表

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | int | 主键 |
| `username` | varchar | 用户名（唯一） |
| `password` | varchar | 密码 |
| `email` | varchar | 邮箱 |

> ⚠️ **已知缺陷**：密码目前是**明文存储**（课程要求是"加密写入"，我做的是简单编码，**强度不够**）。应改为 BCrypt 哈希。

### 8.2 行程表（我新增）

```sql
create table trip (
    id          int auto_increment primary key,
    username    varchar(64)  not null,   -- ★ 归属人（越权防护的基础）
    title       varchar(120) not null,   -- 标题（超长自动截断）
    content     text         not null,   -- 正文
    create_time datetime     not null,
    index idx_user (username)            -- ★ 按用户查是最高频操作
);
```

### 8.3 景点表（课程要求）

用于热门推荐与目的地搜索，支持按**名称 / 城市 / 分类 / 关键词**模糊匹配。

## 九、我在这个产品上还没做到的

| # | 缺什么 | 影响 |
|---|---|---|
| **1** | **Agent 只有方案，没有代码** | 目前仍是"LLM 调用"，**不是 Agent** |
| **2** | **密码明文存储** | 应该加 BCrypt 哈希 |
| **3** | **数据库连接信息硬编码在 Java 里** | 应移到配置文件或环境变量 |
| **4** | **无连接池、无 ORM** | 每次新建连接，**并发上来会成瓶颈** |
| **5** | **无多轮上下文** | 现在一问一答，**不记得上一句**（Memory 只设计了方案） |
| **6** | **无单元测试** | 全靠手工点页面验证 |
| **7** | **`webapp/` 下有旧版残留** | 还硬编码着 `localhost:8081`，是改造前的痕迹 |
| **8** | **没有量化目标** | 文档里没有"规划耗时从 X 降到 Y"这类指标 |

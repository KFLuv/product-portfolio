## 二、我修掉的 4 个真实缺陷 ⭐

> **这四条是这份报告最有价值的部分。**
> 它们的共同点是:**功能"看起来能用"，其实一句都没生效。**

---

### 缺陷 1：用户信息写死，谁登录都显示同一个人

| | |
|---|---|
| **改造前** | `ChatServlet.java:54` — `String jsonResponse = "{\"name\":\"杨博全\",\"email\":\"...\"}"` |
| **代码原注释** | *"原来这里写死了"杨博全"，谁登录都显示同一个人；现在从 session + 数据库取。"* |
| **问题本质** | **这是个"演示时看不出来"的 bug** —— 你用自己账号登录，界面上确实显示你的名字（因为就是你）。换个人登录才发现不对 |
| **改造后** | `ChatController.myInfo()` 从 `session` 取 `loginUser`，再去数据库查邮箱；未登录返回 `login=false` |
| **顺带修的体验** | 未登录也**返回 200**，让前端自己决定怎么提示 —— *"不至于控制台一片红"* |

**改造后的代码逻辑：**

```java
@PostMapping(value = "/myinfo", produces = "application/json;charset=UTF-8")
public Map<String, String> myInfo(HttpSession session) {
    String username = currentUser(session);
    if (username == null) {
        user.put("login", "false");   // ← 未登录不报错，返回状态让前端处理
        return user;
    }
    user.put("login", "true");
    user.put("name", username);
    user.put("email", queryString("select email from user where username = ?", username));
    return user;
}
```

> **产品视角的收获**：**"写死的默认值"是最危险的一类缺陷** —— 它让功能在开发者自己的机器上永远显示正常。

### 缺陷 2：改密码功能是假的，一个字都没落库

| | |
|---|---|
| **改造前** | 只比了一下"新密码"和"确认密码"是否一致，就返回"成功" |
| **代码原注释** | *"原来这里只比了一下两次密码是否一致就返回"成功"，一个字都没落库。"* |
| **问题本质** | **用户以为改成功了，其实什么都没发生** —— 下次登录还是老密码 |
| **改造后** | ① **先验当前密码** ② 再校验两次新密码一致 ③ **真正执行 UPDATE** |

**改造后的三道校验：**

```java
// 1. 校验当前密码，防止别人拿到页面就能改密码
if (!Objects.equals(currentPassword,
        queryString("select password from user where username = ?", username))) {
    return fail(result, "当前密码不正确");
}

// 2. 要改密码时，两次输入必须一致
if (changePassword && !Objects.equals(newPassword, confirmPassword)) {
    return fail(result, "新密码和确认密码不匹配");
}
if (!changePassword && !changeEmail) {
    return fail(result, "没有需要修改的内容");
}

// 3. 落库（用占位符而不是拼字符串，避免 SQL 注入）
MySQLUtil.executeUpdate("update user set password = ? where username = ?", newPassword, username);
```

> **产品视角的收获**：**"返回成功"不等于"真的成功"。**
> 这是我在这个项目里最重要的一课 —— 后来我做 FaultDetect 时，专门给每条结论加了"**反证条件**"，就是为了防止这种"看起来成功了"的情况。

### 缺陷 3：AI 对话是假的

| | |
|---|---|
| **改造前** | 硬编码模板 —— 不管问什么都回答"1. 第一天参观当地著名景点 / 2. 第二天体验当地美食..." |
| **改造后** | 接入真实大模型，走 OpenAI 兼容的 `chat/completions` 协议 |

**改造后的关键设计：**

| 设计项 | 做法 | 为什么 |
|---|---|---|
| **厂商可切换** | 只读 `ai.base-url` / `ai.api-key` / `ai.model` 三项 | 智谱、讯飞星火、硅基流动、阿里百炼、DeepSeek、Groq 全兼容这套协议 |
| **代码自动补路径** | `base-url` 填到域名级，代码自动补 `/chat/completions` | 少填一个字段就少一个出错点 |
| **人设约束** | `SYSTEM_PROMPT` 限定"专业的中文旅行规划顾问" | **避免答成通用百科** |
| **配置校验** | `isConfigured()` 三项都填了才算可用 | 缺任何一项就走本地模板 |
| **降级不挂** | 未配置或调用失败 → 返回提示，**功能不挂** | 保证 demo 可演示 |

**人设提示词（这是产品设计，不是技术细节）：**

```java
private static final String SYSTEM_PROMPT =
        "你是「旅行助手」，一位专业的中文旅行规划顾问。"
                + "请用中文回答，语气亲切专业，条理清晰。"
                + "涉及行程时按天给出安排，并适当给出交通、美食、注意事项方面的建议。"
                + "如果用户的问题与旅游无关，也可以正常回答，但要简短。";
```

> **最后一句"与旅游无关也可以回答，但要简短"是我特意加的** ——
> **既不让它硬拒答（体验差），也不让它跑偏成通用百科（丢定位）。**

### 缺陷 4：无越权防护

| | |
|---|---|
| **改造前** | 无行程功能（所以也没有这个问题） |
| **新增功能时** | 行程本要能"存、查、删" —— **但只要按 `id` 查，改个 id 就能看别人的行程** |
| **改造后** | 四个接口**全部**按 `username` 限定 |

**关键代码（读单条行程）：**

```java
String sql = "select id, title, content, create_time from trip where id = ? and username = ?";
// ...
pstmt.setInt(1, id);
// ★ 同时限定 username：就算前端伪造 id，也查不到别人的行程
pstmt.setString(2, username);
```

**删除同理：**

```java
int rows = MySQLUtil.executeUpdate("delete from trip where id = ? and username = ?", id, username);
if (rows <= 0) {
    return fail(result, "行程不存在或已被删除");
}
```

> **产品视角的收获**：**权限校验不能只做在"入口"，要做在"每一条数据"上。**
> 这一课后来直接用在了我做招聘系统时的"只读账号后端强制拦截"。

## 三、我新增的功能：行程本

### 为什么加这个功能

**课程只要求"聊天问答"，但我的判断是:AI 给的建议如果不存下来，下次就找不到了。**

> **一个只会聊天、不留痕迹的助手，用第二次就要重新问一遍。**

所以我在课程要求之外加了**行程本**。

### 功能设计

| 接口 | 作用 | 关键设计 |
|---|---|---|
| `POST /trips/save` | 保存行程 | 内容为空拒绝保存；标题超 120 字自动截断；为空则命名"未命名行程" |
| `POST /trips/list` | 我的行程列表 | **最新的排前面**（`order by id desc`）；只返回 id/标题/时间（不带正文，列表更轻） |
| `POST /trips/get` | 查看完整内容 | 按 `id + username` 双条件查 |
| `POST /trips/delete` | 删除 | 按 `id + username` 删；删不到明确提示"不存在或已被删除" |

**接口设计的两个取舍：**

| 取舍 | 理由 |
|---|---|
| **列表不返回正文** | 正文可能很长，列表页只需要标题和时间 —— **减少传输量、加快列表加载** |
| **未登录直接拒绝** | "请先登录后再使用行程本" —— **不给匿名用户存数据的可能** |

### 数据库设计

```sql
-- 行程表
create table trip (
    id          int auto_increment primary key,
    username    varchar(64)  not null,   -- ★ 归属人
    title       varchar(120) not null,   -- 标题（超长自动截断）
    content     text         not null,   -- 正文
    create_time datetime     not null,
    index idx_user (username)            -- ★ 按用户查是最高频操作
);
```

> **`username` 这一列是整个越权防护的基础** —— 所有查询都以它为前提。

## 四、Harness 层面的改造（让 AI 用得住）

> **"接通了模型"和"能稳定用"是两件事。** 后者要靠这些。

| # | 改造项 | 不做的后果 |
|---|---|---|
| 1 | **配置为空时兜底** | 评审/演示时没配 Key，**整个功能直接挂** |
| 2 | **调用异常降级** | 模型超时 / 欠费 / 网络断，**接口 500** |
| 3 | **超时控制** | 前端一直转圈，用户以为死了（`connectTimeout=10s` / `timeout=60s`） |
| 4 | **厂商可切换** | 某家涨价或限流就动不了（**换三行配置**） |
| 5 | **人设约束** | 答成通用百科，**丢掉旅游助手的定位** |

## 五、我还设计了 Agent 方案（文档已完成，代码未实现）

> **诚实说明:这部分只有设计文档，还没写代码。**

### 为什么想到这个

课程版本只是"**调用大模型**"，不是"**Agent**"。我研究清楚区别之后，写了一份完整的接入方案。

**判断标准（这是关键）：**

| | 普通 LLM 调用 | Agent |
|---|---|---|
| 模型输出 | 一段文字 | 可能是"**我要调用 `searchDestination`**" |
| 谁来执行 | 没人 | **我的 Java 代码** |
| 执行完 | 结束 | **结果塞回去，再问一次** |

> **分水岭就是 Tools —— 模型能不能"决定去调用某个函数"。**

### 我设计的方案（四步）

| 步 | 做什么 |
|---|---|
| **1** | 把现有能力封装成工具：`searchDestination`（查景点）/ `saveTrip`（存行程）/ `listTrips`（列行程）—— **全部复用已有代码，不重写** |
| **2** | 请求里带上 `tools` 清单（JSON Schema），`tool_choice: auto` |
| **3** | 写 **Agent 循环**：问模型 → 有 `tool_calls` 就执行 → 结果塞回 → 再问（**`MAX_ROUNDS = 5` 防死循环烧钱**） |
| **4** | 暴露 `POST /agent/chat`，前端只改一个 URL |

### 我在方案里写下的 8 条踩坑清单

> **这些是真正的坑,不是抄文档能抄到的。**

| # | 坑 | 后果 |
|---|---|---|
| 1 | **必须设 `MAX_ROUNDS`** | 模型反复调工具 → **一直循环、一直扣钱** |
| 2 | **工具执行必须 try-catch** | 工具抛异常时把错误**当作工具结果返回**，模型能自己纠正；否则整个接口 500 |
| 3 | **`arguments` 是字符串不是对象** | 必须再 `readTree()` 解析一次 |
| 4 | **`tool_call_id` 必须回填** | 和模型给的 `id` 不一致，**厂商直接报 400** |
| 5 | **越权防护** | 带用户数据的工具，`username` **必须后端从 session 取，绝不能让模型或前端传** |
| 6 | **成本与延迟** | 带工具的请求更慢更贵 —— **能一次问完的别用 Agent** |
| 7 | **超时** | Agent 循环总耗时是各轮之和，前端要提示"可能需要几十秒" |
| 8 | **配置为空要兜底** | 三项缺任何一项就走本地模板 |

> **完整方案见 [`源码/docs/技术提炼.md`](源码/docs/技术提炼.md)。**

## 六、关于 MCP：我判断目前不需要

我了解过 MCP（Model Context Protocol）—— 它是让 AI 应用统一接外部工具的接口标准，可以理解为"**AI 工具的 USB 接口**"。

**但这个项目我判断不需要，理由:**

| 判断依据 | 我的情况 |
|---|---|
| 工具数量 | 只有 3 个 |
| 工具位置 | 全在自己的代码库里 |
| 是否需要第三方复用 | 不需要 |

> **所以直接写 Java 方法更简单。工具超过 10 个、或需要接现成第三方工具时再上 MCP。**
>
> **这一条也是产品判断:不是所有新技术都要往产品里堆。**

| # | 缺什么 | 影响 |

| **1** | **Agent 只有方案，没有代码** | 目前仍是"LLM 调用"，**不是 Agent** |
